## Development-to-Docker update procedure

1. Commit or stash local source changes.
2. Run `git fetch --prune origin`.
3. Inspect `git diff --name-status HEAD..origin/main` for overlap with production patches.
4. Run `git pull --ff-only` after the overlap review passes.
5. Reapply only changes that are still absent from upstream.
6. Prefer the official release package and lockfile when upstream contains the same dependency fix.
7. Align `CODELOGICX_VERSION`, `CODELOGICX_IMAGE_TAG`, and `CODELOGICX_MIGRATION_COMPATIBLE_VERSION` with `package.json`.
8. Keep credentials and topology values unchanged during version alignment.
9. Run `bash update.sh --check`.
10. Use `--allow-dirty` only for reviewed production changes that are not yet upstream.
11. Run `bash update.sh --yes` after the check succeeds.
12. Do not bypass a failed verification image, backup, migration, seed, replacement, or health check.

## Production verification

Verify these items after the update:

- The public health endpoint.
- Administrator login.
- The GitHub Dashboard.
- Authenticated WebSocket-only connections.
- Redis returns `PONG`.
- `/storage` exists and the API user can read and write it.
- The running API and web image tags match the release.
- The SQL backup and its SHA-256 file exist.
- Deployment metadata records the expected source commit and dirty state.

Keep the named recovery stash until all public checks pass. Keep the updater backup and deployment metadata after verification.

## Reproducibility note

A production image built with local patches is not reproducible from the upstream commit alone. The deployment metadata must keep the dirty source state until those patches move upstream.
